# Mem^p: Exploring Agent Procedural Memory

## Metadata
- **Authors:** Runnan Fang, Yuan Liang, Xiaobin Wang, Jialong Wu, Shuofei Qiao, Pengjun Xie, Fei Huang, Huajun Chen, Ningyu Zhang
- **Venue:** arXiv preprint
- **Year:** 2026
- **Links:** [Paper](https://arxiv.org/abs/2508.06433) | [Code](https://github.com/zjunlp/MemP)
- **PDF:** `../papers/pdfs/2508.06433v4.pdf`

## Summary

LLM-based agents suffer from brittle procedural memory that is either hand-crafted as prompt templates or implicitly frozen in model parameters. This paper proposes **Mem^p**, a task-agnostic framework that treats procedural memory as a first-class optimization object, systematically studying strategies for **Build**, **Retrieve**, and **Update** phases. During Build, past agent trajectories are distilled into either verbatim step-by-step traces, high-level script-like abstractions, or a combination ("Proceduralization") that interleaves both; during Retrieve, cosine similarity over task embeddings selects relevant memories, with keyword-averaged vectors (AveFact) outperforming raw query vectors; during Update, an error-correction (Adjustment) strategy that reflects on failed retrievals and revises memories in-place outperforms both vanilla append and validation-only filtering. The memory store is modeled formally as an MDP with add/delete/update operations.

Evaluated on TravelPlanner and ALFWorld using GPT-4o, Claude-3.5-Sonnet, and Qwen2.5-72B, Mem^p consistently improves task accuracy ~50% and cuts execution steps ~50% over no-memory baselines. The Proceduralization build strategy (trajectory + script) outperforms either alone, and the Adjustment update strategy compounds improvements near-linearly across task batches. A key cross-model result: procedural memory built by GPT-4o can be migrated to Qwen2.5-14B (5-parameter gap), yielding +5% task completion and -1.6 avg steps — confirming that procedural knowledge is transferable across models without retraining.

## Relevance to Thesis

Directly addresses all three thesis focus areas:

- **Memory Controller**: The Build/Retrieve/Update lifecycle is a concrete implementation of procedural memory management. The dual-level representation (trajectory + script) is directly relevant to designing a memory controller that maintains both episodic and abstracted procedural knowledge. AveFact keyword retrieval suggests hybrid dense/sparse retrieval for procedural schemas.

- **Educability / Learning from Experience**: The Adjustment update strategy (reflect on failure, correct memory) is a form of online self-education. The near-linear accuracy improvement across task batches demonstrates measurable learning-from-experience, a direct operationalization of educability.

- **Knowledge Transfer**: The GPT-4o → Qwen2.5-14B transfer experiment is a direct empirical proof-of-concept for cross-model procedural knowledge transfer — procedural memory as a distillation artifact that migrates independently of model weights. This is a strong baseline for the thesis.

Is a baseline to compare against for procedural memory controller design.

## Method Details

**Architecture:**
- Memory store: key-value pairs where key = task description embedding, value = procedural memory
- Build strategies: (1) Trajectory — store verbatim gold traces; (2) Script — LLM-distilled abstract procedure; (3) Proceduralization — both combined
- Retrieve strategies: (1) Random; (2) Query-vector cosine similarity; (3) AveFact — extract keywords via LLM, average keyword-vector similarities
- Update strategies: (1) Vanilla — append all new trajectories; (2) Validation — append only successful trajectories; (3) Adjustment — when retrieval causes failure, revise memory in-place using reflection on the erroneous trajectory

**Training/Setup:**
- No fine-tuning; all memory operations are prompt-based at inference time
- Memory refreshed every t tasks on the test set
- Retrieval uses top-k cosine similarity over sentence embeddings

**Evaluation:**
- TravelPlanner: Commonsense Constraint (#CS) and Hard Constraint (#HC) scores
- ALFWorld: dev/test success rate and step count
- Ablations across all Build × Retrieve × Update strategy combinations

## Gaps & Open Questions

### Limitations (acknowledged)
- Retrieval restricted to vector-similarity (cosine); BM25 and other retrieval methods not explored
- Depends on explicit benchmark reward signals; cannot evaluate task success in open-ended real-world settings where rewards are sparse or absent

### Limitations (observed)
- Cross-model transfer only tested GPT-4o → Qwen2.5-14B on one direction; no bidirectional or same-family comparisons
- No analysis of memory quality degradation over time (does the store get noisy as it scales?)
- Procedural memory is task-type-specific; no cross-domain transfer studied (e.g., ALFWorld memory helping on TravelPlanner)
- Retrieved memory count has an optimal range (~10-12); mechanism for why excess memories hurt is underexplored
- No comparison to RAG over raw trajectories as a non-procedural baseline

### Unexplored Directions
- **Cross-domain procedural transfer**: Can procedural memory from one task type generalize to structurally similar but superficially different tasks?
- **Memory compression**: As the store grows, which memories to merge, prune, or abstract further? Hierarchical memory consolidation.
- **Weak-to-strong reversal**: Can a weaker model's memory augment a stronger one (e.g., diverse exploration strategies)?
- **Structured memory schemas**: Current key-value pairs are flat; could ontology-structured procedural memory improve precision of retrieval?
- **Active forgetting**: Adjustment corrects bad memories but doesn't study catastrophic forgetting under domain shift.
- **POC**: Implement MemP Build+Retrieve+Update pipeline as the procedural memory module of thesis memory controller; test cross-model transfer protocol with different architecture pairs.
